# 5차시. 저장하지 못한 피드백을 보관하고 재시도하기

## 1. 학습목표

[오늘 수업 안내](../TODAY_GUIDE.md)를 읽습니다. DB에 저장하려는 순간 연결이 끊겨도 작성한 평가가 사라지지 않게 합니다. Day20의 질문 재시도와 달리, 이번에 보관하는 것은 **평가 저장 요청**입니다.

- 다음 평가 저장만 한 번 실패시키고 미확정 평가를 확인할 수 있습니다.
- 같은 답변 번호와 내용으로 다시 저장할 수 있습니다.
- 재시도 한도에 도달해도 취소하고 평가를 다시 작성할 수 있게 바꿀 수 있습니다.

## 2. 중요 알고리즘 및 코드를 읽을 때 반드시 알아야 할 내용

AI 답변은 잘 받았는데 평가 저장만 실패했습니다. 이때 평가를 지워 버리면 다시 선택해야 하고, 재시도할 때 새 번호를 만들면 같은 평가가 여러 행으로 늘 수 있습니다.

`pending_feedback`은 제출했지만 저장을 확정하지 못한 평가입니다. 입력 중인 폼 초안과 구분합니다. 저장에 성공하면 미확정 값을 비우고, 실패하면 같은 내용을 그대로 남깁니다. 재시도는 같은 번호를 사용하며 DB의 `ON CONFLICT` 정책이 한 행을 유지합니다.

| 상태 | 화면에서 할 수 있는 행동 | 보관 내용 |
| --- | --- | --- |
| 저장 전 | 폼 작성·저장 | 작성 중인 선택값 |
| 저장 실패 | 재시도·취소 | 제출한 평가와 고정 답변 ID |
| 저장 성공 | 다른 평가 작성 | 성공 기록, 미확정 값 해제 |

`persist_record()`가 저장 시도를 하나 늘린 뒤 실제 DB 함수를 호출합니다. `피드백 취소`는 미확정 요청만 버리며 이미 DB에 저장된 평가를 삭제하지 않습니다. 미확정 평가가 있으면 새 평가 저장은 먼저 처리하라는 안내가 나오지만, 여행 질문은 계속할 수 있습니다.

참고: [psycopg 트랜잭션](https://www.psycopg.org/psycopg3/docs/basic/transactions.html), [PostgreSQL INSERT와 ON CONFLICT](https://www.postgresql.org/docs/current/sql-insert.html).

`GROQ_API_KEY`, `DATABASE_URL`을 입력하고 로컬에서만 `SHOW_DEMO_TOOLS=true`로 설정합니다. Local URL을 열어 **피드백 테이블 준비**를 누릅니다. 클라우드에서는 재현 도구를 숨기도록 `false`를 사용합니다. 종료는 Ctrl+C입니다.

### 1단계. 저장 전 연결 실패 한 번 재현

‘강릉에서 도보와 버스로 이동할 반나절 코스를 제안해 주세요’라고 보내 완성 답변을 만듭니다. 사이드바의 **다음 피드백 저장 한 번 실패**를 누릅니다. 이 장치는 저장 전에만 실패를 일으키며 Groq 질문이나 DB 테이블 준비를 실패시키지 않습니다.

답변에 평가와 이유를 선택하고 동의한 뒤 **피드백 저장**을 누릅니다. 다음 안내와 답변 ID를 확인합니다.

> 저장하지 못한 피드백이 있습니다. 재시도하거나 취소하세요.

저장 시도는 1회이며 해당 ID의 새 DB 행은 아직 없습니다. **피드백 재시도**를 누르면 실패 예약이 이미 소모되어 DB에 저장됩니다. 미확정 안내가 사라지고 답변 아래에 저장 완료가 보입니다.

### 2단계. 재시도 허용 함수 바꾸기

현재 `retry_allowed()`는 `return True`이므로 실패가 계속되면 수동 재시도를 계속 허용합니다. 다음 함수로 교체합니다.

```python
def retry_allowed(attempts):
    return attempts < 3
```

`attempts`는 최초 저장을 포함한 시도 횟수입니다. 1회와 2회 뒤에는 다시 시도할 수 있고, 3회가 되면 재시도 버튼이 비활성화됩니다. 취소 버튼은 남겨 잘못된 설정이나 입력에서 빠져나올 수 있게 합니다.

### 3단계. 성공 뒤 같은 번호의 행 확인

같은 답변의 평가를 다시 저장하고 SQL Editor에서 해당 ID의 행수를 봅니다. 아래의 `화면의_답변_ID`를 실제 화면 번호로 바꿉니다.

```sql
select message_id, count(*)
from public.kdt_travel_feedback
where message_id = '화면의_답변_ID'
group by message_id;
```

행수는 1이어야 합니다. 이번 한 번 실패 장치는 저장 전에 멈추므로 저장 후 응답 유실을 재현한 것은 아닙니다. 실제 재평가가 같은 ID를 갱신하는 것도 따로 확인합니다.

### 예상 결과

| 조작 | 결과 |
| --- | --- |
| 한 번 실패 예약 후 저장 | 미확정 평가 안내, 저장 시도 1회, DB에 새 행 없음 |
| 피드백 재시도 | 같은 ID로 저장, 미확정 안내 해제 |
| 같은 답변 다시 저장 | 해당 ID의 DB 행수 1 |
| 수정 후 실패가 총 3회 지속 | 한도 안내, 재시도 비활성, 취소 가능 |
| 피드백 취소 | 미확정 평가만 해제, 기존 DB 기록 유지 |

## 4. 복습 과제

실패 예약 뒤 저장한 평가의 ID를 적고, 재시도 성공 후 SQL Editor의 ID와 비교합니다. 새 번호가 생기지 않아야 하는 이유를 한 문장으로 설명합니다.

미확정 평가를 **피드백 취소**로 버린 뒤 이유를 바꿔 다시 작성합니다. 정상 저장 안내와 DB의 최신 평가를 확인합니다. 다음 차시에는 재현 도구를 기본적으로 숨긴 파일을 사용합니다.
